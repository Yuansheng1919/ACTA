# engine/assembly · 表驱动装配（装配层）

把「往模型上下文里装什么、放哪条通道、排第几、多少字」从代码里的 if 搬到一张表；
装配器只照表执行。**本目录不依赖 engine 之外的任何东西，也不改 engine 现有行为。**

## 为什么要有这一层

硬编码装配有三个反复出现的毛病，都是实测撞出来的：

1. **通道判据藏在分支里**：同一份内容放 `tool` 能过、放 `user` 被整体拒绝；一旦写成 `if (channel === "user")`，
   下一个改代码的人就会在别处再加一个 if，口径逐渐分叉。
2. **顺序与分隔符没法评审**：产物是几百行字符串，改了哪几段、少没少内容，只能靠肉眼。
3. **"差不多"能过**：没有逐字判据，装配漏一节、少一个换行，测试照样绿。

表 + 逐字比对解决这三件事：通道写在表里；顺序写在表里；判据是"两份产物一个字节都不能差"。

## 目录

```
engine/assembly/
  primitives.mjs            四个内容变换原语（纯函数，无 IO）
  assembler.mjs             表驱动装配器：assemble(table, {body, jobDir})
  reference.mjs             参照实现（硬编码顺序的"老路"），只用来做对照
  verify.mjs                逐字比对：表输出 vs 参照输出
  tables/play.example.json  示例表（AssemblyTable/1）
  samples/                  合成样本：请求、素材池、规则、剔除关键词
  templates/                user 通道指令模板
```

## 跑

```bash
node engine/assembly/verify.mjs     # Node ≥ 18，零依赖、零网络、零模型调用；退出码 0 = 通过
```

预期输出：

```
| 用例 | inputMd | taskText | 覆盖率 | 结论 |
| example | 同 15803 字 | 同 573 字 | 满 | PASS |
| memory | 同 15803 字 | 同 655 字 | 满 | PASS |
| no-last-user | 同 13628 字 | 同 573 字 | 满 | PASS |
| empty-card | 同 11956 字 | 同 573 字 | 满 | PASS |
- 确定性（同请求 3 次）：一致
- 结论：PASS · 逐字相同（字符级 + 字节级）
```

## 判据（四条，缺一不算过）

| 判据 | 意义 |
|---|---|
| 字符级全等 | 表输出与参照输出逐字符相同 |
| 字节级全等 | UTF-8 字节序列相同（防编码/换行差异蒙混） |
| 覆盖率 | 产物每个字符都能归属到某一节；节间只允许表里声明的分隔符 |
| 确定性 | 同一请求跑 3 次结果完全一致 |

统计口径（各节字数、切片条数、剔除字数）也必须一致——不一致但正文相同，说明有一处"算了没记"。

## 两条设计约定

1. **`when` 只允许结构化判定**（`eq/ne/gt/gte/lt/lte/truthy` + `all/any/not`），不许写 JS 表达式。
   表和代码的边界因此是硬的：表没有能力执行任意代码。
2. **同一来源可以出现两处**。例：末条消息既在「★当前场景」里按末 N 字截断出现，又在楼层列表里原样出现。
   表里就是两节指向同一来源、取法不同——不需要为它发明"引用"语法。

## 与 engine 的关系

本目录是独立模块，`verify.mjs` 不碰 engine 的其他文件。要接进现有流程时：

1. 用 `assemble(table, {body, jobDir})` 替换现有的内联拼装；
2. 把原来散落在代码里的常量（标题字面量、截断长度、通道开关）搬进表；
3. 跑一次 `verify.mjs` 确认与 `reference.mjs` 逐字相同，再跑现有验收用例。

`schema` 细节见 `docs/装配表-schema.md`。

## 已知边界

- 只产出两份字符串（`inputMd` / `taskText`），不直接调用模型，也不写产物文件；
- 抽样是**确定性**的（按楼层号滑窗，不随机），换一轮必然换类别，但同一轮结果可复现；
- 素材池与规则文本由调用方传入（表里给路径），本模块不做内容判断——
  什么内容能进哪条通道由产品口径决定，代码只保证"照表执行"。
